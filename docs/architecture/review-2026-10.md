### 2.2 The save and restore seam (finding 9)

**What happens (by reading).** A failed load gives Sundial an empty document in memory (`SundialService.cs:135-139`).
Every write is then refused (`SundialService.cs:622`), so a damaged session cannot overwrite the user's files. The
restore pinch calls `TryRestoreBackup` and drops its result (`FirstRunWizard.cs:223`). That method copies the first
backup it finds over `save.json` (`SundialService.cs:403-408`) and leaves the reload to its caller. Nothing reloads:
the service is built once (`SundialController.cs:228`), the wizard caches it (`FirstRunWizard.cs:108`), `Outcome` has
no setter outside the constructor (`SundialService.cs:131`), and `Update` keeps forcing the prompt visible while the
outcome is `Failed` (`FirstRunWizard.cs:175-181`). The next launch loads the copied backup.

**How bad.** In the common case it is **a stale prompt until restart, not data loss**: the pinch looks dead, the user
cannot start the first run or tend (`FirstRunWizard.cs:218-225`, `:267-269`), and a restart shows the restored record.
The user is stuck until they think to restart. Gate S6 forbids being stuck over 5 s, but only on the canonical journey
(`PLAN.md:102`), and a damaged save is off that journey, so no gate catches this. There are two data-loss edges, both
by reading:

1. **The newest save can be overwritten.** `Load` fails with step `read` on any IO exception (`SaveStore.cs:190`),
   for example a file held open by a sync client or a virus scanner. The live file is then intact and newer than
   `save.prev1.json`. The restore copies `prev1` over it with `overwrite: true` (`SundialService.cs:408`) and keeps no
   copy, so the last write, typically the last tend, is gone.
2. **An unreadable backup loops forever.** The copy checks neither parse nor schema. If `prev1` is damaged too, the
   next launch fails again, `prev1` still exists, and every restore picks it again (`SundialService.cs:404`). It never
   tries `prev2` or the snapshot. Terrarium stops at the first backup as well: `FirstBackup` returns `prev1` whenever
   it exists (`GardenService.cs:347-356`), and `TryRestore` gives up when that file does not parse
   (`GardenService.cs:305-306`). Terrarium does adopt a good backup in place (`GardenService.cs:314-327`,
   `JarRitualController.cs:742-752`), and its PlayMode test checks the restored garden (`DaysPlaybackTests.cs:164-209`).
   Sundial's test checks only that the prompt shows (`FirstRunTests.cs:132-134`).

**Should core own restore-and-reload?** Core should own **restore**: choose a readable backup, read it through the
same parse, version and migration path as `Load`, keep the damaged file, write atomically, and return the loaded
document. Core cannot own the **reload**, because the document becomes app state differently in each app (Sundial
rebuilds its ledger, deferred tend, gratitude record and focus block, `SundialService.cs:135-175`). Once restore
returns the document, reload is "adopt this document in place", which Terrarium already does. The four file names
that Sundial retypes (`SundialService.cs:403-406`) are `SaveStore` constants (`SaveStore.cs:117-121`). Proposal 2.

### 2.3 DialView and JarView: where to split (a proposal only)

Both are one MonoBehaviour that is the locked look's presenter, every art spike as a token-switched variant, the
capture-state parser and the edit-time builder at once. The sizes are in section 1. The split runs along five seams
(proposal 6): the locked look against comparison looks; state presentation; capture-state parsing; edit-time building;
and, for the dial, CPU mask baking. The sprint composites stack nearly every spike (`DialView.cs:805`,
`JarView.cs:493-508`). So the look lock decides which half survives. Splitting before the lock moves code that the
lock may delete.

## 6. Decisions to capture

Candidates only; `docs/decisions/` belongs to another charter. Decisions 0001 to 0003 stand as given.

1. Acknowledging "Continue?" never starts a breath: in both apps the hand releases and pinches again (the jar's rule, `JarRitualController.cs:763-767`).
2. A Sundial plant's lifetime counts every live kept day since the habit was created, whatever the clock says today; undo still removes a day.
3. Restore is a core `SaveStore` operation: it tries `prev1`, `prev2` and then the snapshot through `Load`'s own path, keeps the damaged file, and returns the document for the app to adopt without a restart.
4. While no Unity licence exists, a purely additive core change (new files or members, no signature or behaviour change) merges on `dotnet test shared/core-dotnet` alone, and the next Unity compile of both apps confirms it (`PLAN.md:184` for this period).
5. Step B of an extraction runs only in a session that can compile Unity and run the suites that name the file; until then the app copy is frozen.
6. An app file with no engine import is compiled in place by a dotnet test project until it moves to core, so the dotnet build is the rule-4 tripwire.
7. Once the owner locks a look, art spikes are deleted rather than refactored; a view keeps the locked look plus at most one comparison look for side-by-sides.
8. The capture rig (camera, plate, world-plate hiding) has one public home in `com.gardenvr.capture`, and app editors and PlayMode tests call it.
9. A new core type never takes the name of an app type (an app namespace would win silently, and Unity compiles cannot be checked here).
10. Milestone 3 reports code lines and duplicate rule sites beside the score, because a refactor commit raises a file's score unless it removes more than `codeLines / (churn + 2)` code lines.
